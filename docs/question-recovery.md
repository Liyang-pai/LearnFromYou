# 追问漏登记的定向修复与课堂恢复

模型有时会输出 `candidate.kind="question"`、`question_id="q2"`，却既没有在本轮 `question_updates` 登记 `q2`，也没有对应的已有疑问。旧逻辑在发言校验时抛出“候选问题不在问题库中”，导致本轮学习记录全部拒绝提交并暂停队列。这里的疑问列表属于学生课堂提问生命周期，与给学生出题的题库无关。

## 恢复规则

1. `ModelClient.generate()` 解析 JSON 后，调用可选的同步结果校验回调。课堂调用使用状态副本做完整预校验，修复期间不提交知识、疑问、事件、处理编号或历史。
2. 追问引用不存在的疑问时，抛出专用 `MissingQuestionError`，携带问题编号，并反馈“请在 question_updates 中补齐对应疑问记录，或将 candidate 改为 silence”。
3. 首次失败会把具体错误、模型刚才的输出一起送入一次修复请求。JSON 格式修复与课堂关联修复共用原有两次请求上限，不在课堂外层再增加自动重试。
4. 最后一次输出若仍仅漏登记追问，将候选替换为 `silence`，完整重新校验其他记录，通过后正常提交。不会自动补建疑问、发送这次追问或增加提问次数；后续课堂内容继续按序处理。
5. 最终 JSON 无法解析、网络失败、无效知识或候选来源、错误的纠正关联、缺少问题关闭依据等错误仍使整轮失败。原状态保持不变，批次保留，等待手动重试。

缺少或为空的问题编号同样按“追问关联不存在”处理，前提是候选正文与来源及其他记录通过校验。已经解决、延期或达到提问次数上限的疑问，继续沿用原有抑制规则。修复期间收到新教师输入，旧候选回复仍会失效；静音时仍更新认知。

## 接口与日志

对外教学设置、模型输出字段、课堂状态和已有消息保持兼容。内部增加 `result_validator(result, final_attempt)` 回调：返回有效的 `StudentResult`，或抛出校验异常；其结果仍需经过课堂提交时的完整校验。

新增调试事件：

- `student_validation_error`：包含尝试编号和具体错误，用于显示自动修复过程，不切换到手动重试状态。
- `student_recovery`：包含跳过原因、原问题编号、来源、尝试编号及“异常追问已跳过，课堂继续”。原始模型输出仍保存在 `llm_output`，不会被静默改写。

成功恢复后只提交一次状态、只记一次教师批次历史，不发送异常回复，也不设置失败批次。真正失败的结果仍触发现有 `error` 和手动重试按钮。

## 离线验证

```sh
./.venv/bin/python -m pytest -q tests/test_question_recovery.py
./.venv/bin/python -m pytest -q
```

固定样例复现已解决的 `q1` 与漏登记的新 `q2`，覆盖修复成功、两次漏登记、最终无编号、两类错误共享预算、无效来源、问题关闭依据、纠正关联、修复时断网，以及新输入撤销旧发言。测试使用内存 HTTP 响应，不读生产课堂日志、不调用外部模型。

浏览器测试启动真实本机服务，但使用模拟 ASR 和 `MockTransport` 完全替换云端模型；前端副本和课堂日志均位于系统临时目录，不要求预先启动服务或安装 ASR：

```sh
node tests/question_recovery_browser.cjs
```

需要 Node.js、Playwright 和 Chrome；可用 `NODE_PATH` 指定包目录，`CHROME_PATH` 指定浏览器路径，`LFY_TEST_PYTHON` 指定 Python。测试确认页面连续漏登记后无需手动重试、不发出异常追问，且下一段讲授正常更新认知。结束时输出临时截图路径。

本修复集中处理追问关联异常，不调整画像和对话历史输入，也不处理教学设置残留。修复是否生效可通过离线测试确定，无需重新发送用户实际课堂数据。

2026-10-12 验证结果：新增恢复专项测试 13 项通过，完整回归 209 项通过、3 项跳过；真实 Chrome 与离线课堂服务的联调通过，模型文件检查通过。更新后需重启后端并刷新页面，以加载新的课堂校验与恢复逻辑。
